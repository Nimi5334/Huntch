## What is Huntch

Huntch is a **pure patient-reactivation tool for dental and aesthetic clinics in Israel**. It holds every patient's profile (treatment history + payments) and, on a recurring cadence, generates a **personalized message per patient to bring them back** — that is the app's one job. Nothing else.

There is **no scoring/matching system**, **no job-board concept**, **no AI brain/FAQ/simulation trainer**, **no escalation inbox**, **no ROI/activity dashboard**, and **no automation-settings page** — all of that was built during earlier iterations and then deliberately deleted (2026-07-11) to keep the product "נטו" (purely) about periodic reactivation. The whole product was originally pivoted (2026-07-10) from an F&B staffing app into a clinic platform; some CSS class names (`.cand`, `.prof-*`, `.dna-*`) are inherited from that lineage and reused for the shared design system only.

**Stage:** MVP — a two-screen demo product, working end-to-end on the local/demo path (Zustand + localStorage, auto-login). Multi-tenant Supabase schema + RLS are written and ready to run; WhatsApp live-send and real billing need external setup (see "What's left" below).
**Language:** Hebrew (RTL, `dir="rtl"`, `lang="he"`).
**Operator:** Single clinic per account (e.g. `מרפאת שיניים ד"ר ירון כהן`).
**Deployed:** https://formdna.vercel.app
**GitHub:** https://github.com/Nimi5334/Huntch (branch: master)

## The Product — 2 screens, 1 job

### Home (`/`)
The entire cockpit. Lists every patient as a `PatientCard`:
- **Avatar · name · lead headline/reason** (from `lib/leads.ts` → `generateLead()`, pure & deterministic — incomplete plan → recall-interval elapsed → long-overdue routine visit → "הכל מעודכן").
- **Up-to-date patients** get a green "עדכני" badge, no action.
- **Due patients** get a "ליד" tag plus an inline action, gated by plan (`canUse(clinic, 'auto_outreach')`):
  - **Advanced:** "אשר ושלח" — one tap creates the outreach, approves it, and sends it (approve-before-send; no auto-send without this tap).
  - **Basic:** "העתק הודעה" — copies the personalized draft message so the clinic sends it manually from their own WhatsApp. A small teaser banner nudges upgrade when there are patients due.
- Tapping the card body (not the button) opens the full profile. "+ הוסף מטופל חדש" opens `components/AddPatientModal.tsx`. A search field filters by name/phone.
- There is **no separate tasks/automation/activity page** — everything actionable lives directly on this one list.

### Patient profile (`/patients/[id]`)
- **Lead card** — same headline/reason/draft message as the Home card, with "העתק הודעה" always available and "אשר ושלח" shown only on Advanced.
- **Treatment history** — every `TreatmentRecord` (date, name/category, status, cost).
- **Billing summary** (`lib/billing.ts` → `billingSummary()`) — total billed / paid / outstanding.
- Basic identity fields (phone, last visit, age, consent) and `medicalNotes` if present.

### Header / navigation
No tabs, no bottom nav, no drawer — with only two screens (one hub + one drill-in), there is nothing to switch between. The header is just the logo (→ Home) and an avatar that opens a **profile panel**: clinic identity, patient/outreach stats, and inline **plan switching** (Basic ⇄ Advanced, with trial-countdown banner) plus logout. There is no dedicated Settings or Billing *page* — plan management lives entirely in this panel.

## Data Model — `lib/types.ts`

```typescript
Clinic { id, name, type: 'dental'|'aesthetic', address, operatorName, phone, plan: 'basic'|'advanced', trialEndsAt }
Patient { id, clinicId, name, phone, treatments: TreatmentRecord[], payments: Payment[], medicalNotes, consent, optedOut }
TreatmentRecord { id, date, category, name, status: 'completed'|'planned'|'in-progress', cost, notes }
Payment { id, date, amount, method, treatmentId }
Lead { headline, reason, suggestedCategory, draftMessage }   // derived, not stored
Outreach { id, clinicId, patientId, kind: 'reactivation', status: 'draft'|'approved'|'sent'|'replied'|'declined'|'no_reply', message }
```

`OutreachKind` is a single literal, `'reactivation'` — every message this app sends is a periodic personalized reactivation message. There is no `Escalation`, `BusinessKnowledge`, `FaqEntry`, `VoiceExample`, or `AutomationSettings` type — all deleted along with the screens that used them.

## Membership & Pricing (`lib/plan.ts`)

Two tiers, both showing the full patient database and full personalized leads — the only difference is **who presses send**:

| Tier | Price (placeholder) | Includes |
|---|---|---|
| **בסיסי (Basic)** | ₪149/mo | Full patient database + profiles, personalized reactivation message per patient, **copy + manual send**, patient cap 500 |
| **מתקדם (Advanced)** | ₪499/mo | Everything in Basic **+** the app sends the periodic reactivation message itself with a one-tap approval, unlimited patients, priority support |

- 14-day Advanced trial granted on signup (`clinic.trialEndsAt`).
- `effectivePlan(clinic)` returns `'advanced'` while trial is active even if `clinic.plan === 'basic'`.
- **No dedicated billing page** — plan switching happens inline in the header's profile panel (`store.setPlan()`); real Stripe Checkout wiring is a flagged future step.

## Supabase — Multi-Tenant Security

- **Schema:** `supabase-schema.sql` — `clinics`, `memberships` (maps `auth.uid()` → `clinic_id`), `patients`, `treatments`, `payments`, `outreach`. **RLS is enabled on every clinic-owned table** with policies scoped through `memberships` — one clinic can never read another's data. (The `escalations` table and `knowledge`/`insights` columns were dropped in the 2026-07-11 simplification.)
- **Client-side (`supabase` export):** anon key, respects RLS. **Server-only (`supabaseAdmin` export):** service-role key, bypasses RLS — used only by the WhatsApp webhook to do cross-tenant lookups keyed by `wa_phone_number_id` (each clinic's own registered WhatsApp number identifies which tenant a message belongs to).
- **Demo/local path does not touch Supabase at all** — the whole product runs on Zustand + localStorage with seeded data. Supabase is exclusively the *production* multi-tenant path.
- **Setup:** paste `supabase-schema.sql` into the Supabase SQL Editor, enable Email auth, set env vars (below).

## WhatsApp Integration

| File | Purpose |
|---|---|
| `lib/whatsapp-client.ts` | Meta Cloud API wrapper (`sendText`, `sendButtons`, `sendList`, `normalizePhone`) |
| `lib/outreach-flow.ts` | `deliverOutreach(phone, message)` (best-effort live send) + `processIncomingReply(waPhoneNumberId, fromPhone, text)` (webhook handler: identifies clinic by WA number → marks the matching sent outreach as replied — no AI reply-back) |

## What NOT to do

- ❌ Never reintroduce a "recovery score" or candidate-matching score — this product surfaces plain personalized reactivation leads, not rankings.
- ❌ Never reintroduce the AI brain (FAQ/simulation trainer/auto-answer), escalation inbox, quality-checks, ROI/activity dashboard, or automation-settings page without an explicit new request — they were deliberately deleted to keep the product "נטו" (purely) about periodic reactivation.
- ❌ Never use `JSX.Element` — use `React.JSX.Element` (React 19).
- ❌ Never auto-send outreach without an explicit approve step (approve-before-send is the default autonomy model on Advanced; Basic never auto-sends at all).
- ❌ Never use purple/blue gradients — Chalk & Cedar palette only.
- ❌ Never use emoji as navigation/UI icons — SVG only (inline emoji in copy is fine).
- ❌ Never expose `SUPABASE_SERVICE_ROLE_KEY` or `WHATSAPP_ACCESS_TOKEN` to client components — server-only.
- ❌ Never remove RLS policies or add a table without `clinic_id` scoping.
- ❌ Never hardcode `huntch.co.il` or any domain other than `formdna.vercel.app`.
- ❌ Never use `roundRect()` Canvas API — use manual path construction for browser compatibility.
